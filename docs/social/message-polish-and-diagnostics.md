# 消息布局、滚动与一起听诊断

## 本轮实现顺序与行为

1. 标题和滚动容器分离。左右详情标题下去掉横线，复用小范围渐变模糊；滚动条从标题下方开始。四个分类继续独立保存滚动位置。
2. 双方头像各占固定列，共用中间安全内容区。短文字气泡按内容收缩；图片保持比例，懒加载、解码后显示，失败由用户点击重试。少量完整 Unicode 表情放大，混合文字及未知平台表情标记保留原文。
3. 一起听邀请改为横向卡片，标题、平台来源、说明和接受按钮分层；本人发出的邀请不显示不可用的接受按钮。
4. 向上滚动接近顶部时自动读取历史，不占用顶部放置“加载更早消息”。同一游标限制连续请求，前插沿用稳定消息键及像素锚点。成功发送隐藏状态文字；明确失败的本账号文本显示主题色圆形重发箭头；发送结果未知保留提示，不提供盲目重发。
5. 相邻消息空档达到五分钟或跨本地日期时显示居中的时间分组。单条详细时间悬停淡入，移开淡出，只改变透明度、不参与高度计算；消息间保留十二像素左右间距。日期使用应用语言和原生 Intl：今天只显示时间，昨天和前天使用对应语言，较远的同年消息显示月日，跨年显示年月日。减弱动效偏好关闭过渡。
6. 虚拟列表统一维护贴底，页面不再同时追赶每次追加。首屏直接定位最后一屏；DOM 更新后合并纠正，用户向上输入取消待执行的贴底。历史前插也在 DOM 更新后恢复锚点。监听、测量定时器、RAF 与迟到解码在卸载时回收。

## 保留的请求调整

以下调整解决客户端状态与服务端回显之间的竞态；没有新增或猜测协议参数，也不代表已复刻全部官方协议。

| 操作               | 原有风险                                   | 本轮调整                                                                             | 请求边界                                                                                    |
| ------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------- |
| 手动加歌           | 上次轮询的版本向量可能已落后于其他成员     | 校验官方歌曲详情后、ADD 前读取当前房间与列表，使用最新 version，并再次检查归属及房间 | 复用 roomStatus / roomPlaylist；歌曲已存在则不发送 ADD                                      |
| ADD 确认           | 一次立即读取尚未反映加歌，误报失败         | 发一次 ADD 后最多三次读取确认，额外等待为 0、300、900ms；同房间出现目标歌曲才确认    | 不含网络请求自身耗时；原请求仍有超时、账号及 AbortSignal 保护                               |
| ADD 否定或未知回显 | 未知写入若重发，可能重复或扰乱版本         | 只读核对实际列表；仍未确认时提示稍后查看，不自动重放                                 | HTTP 200 不作为成功证明；读取失败、失效、账号及房间变化仍按原错误处理                       |
| 消息历史           | 顶部手动按钮占用空间、连续输入触发多次请求 | 向上输入触发既有历史读取，页级游标节流与 store 单飞合并                              | 原 time 游标、limit=30、total=true 不变；不新增后台消息上报                                 |
| 失败消息重发       | 新消息身份会产生重复气泡                   | 用户点击后沿用本地 clientId 和原文本调用既有 send                                    | clientId 只在本机合并，不伪造服务端幂等字段；未知、已发送及他人消息不能重发，原发送限流保留 |

ADD 仍发送 `playlistParam` JSON 字符串：`commandType=ADD`、服务端最新版本向量仅递增本账号项、当前 `playMode` 和锚点、增量 `displayList/randomList`。eapi 域名、签名、Cookie/CSRF 管理及加密不变。未将普通播放按钮转换成 ADD；网易云歌曲未入队时指引用户主动“添加到一起听”，非网易云及云盘音源仍受房间保护。

## 续歌、好友与原播放链路

普通一起听窗口下半部分为左右两列，左侧房间歌单、右侧可添加歌曲；各用固定 52px 行高的 SVirtualList，共用排版和主题，独立滚动。歌曲来源选择器位置不变，房间推荐缺失的说明显示在右侧空列表内，已经入队的候选隐藏。两人已经加入时，普通窗口隐藏好友、UID、邀请及复制链接控件，调试入口保留。房员显示跟随状态和手动加歌说明，等待续歌时使用对应提示，不把等待状态宣称为已接管服务器房主。

好友选择器不再依赖消息页是否已加载。主进程读取关注与粉丝各 100 条，互关优先、关注其次、粉丝最后，带标题并去重、自身不入选；最近会话放在备用分组。数据按账号/方向/页短时缓存 60 秒，最多十页，共享同一读取；更多页由用户主动点击，每个方向最多 500 人，不做后台全量扫描。失败时保留最近会话和 UID 输入，可手动重试，账号变化/卸载后丢弃旧结果。只读实测两接口均返回 code=200；参数来源是项目原接口模块，不能称为新抓得的 Windows 原版包。

焦点剪贴板解析出本账号作为 inviterId 的链接时，不打开邀请窗口、不替换已打开窗口、不读取预览元数据、更不入房。主进程预览也拒绝自己邀请；剪贴板去重摘要按登录会话隔离，不将 Cookie 或摘要打印到日志。无法解析出邀请者的短链无法可靠判断自身，继续保留用户主动打开浏览器的兜底。

自动推荐默认开启，本机房主在最后一首正在播放时补一首，沿用既有轮询且每个末曲只自动尝试一次。优先选未入队的房间推荐，耗尽后使用执行账号的每日推荐；个人推荐有 60 秒缓存及并发合并，歌曲详情仅保留最近 600 首。普通下一首不增加预读；当手动点到队尾时，先重新核对房间并补歌，再发原 NEXT。未知 ADD 不重放，确认未完成时不切向未入队歌曲。房员不在播放途中抢写，只沿用原四秒等待、重新读取和选举后的结束接续；没有官方双人口味算法或离线房主推荐接口证据。

房主可在歌曲来源菜单选择“仅播放房间歌单”，复用设置的 togetherAutoRecommend 开关并持久化。关闭后自然结束和末曲下一首都不主动加推荐，仍按房间既有播放模式续播；仍可显式添加歌曲。切换回其他来源恢复自动推荐。服务端心动及未知列表模式保持原处理，不以该本地开关替换官方模式。

歌曲菜单、歌单、已加载列表、首页歌单/专辑/继续播放卡片和原加入队列入口共用房间增量加入。一次最多 500 首，按网易云官方来源过滤、去重并排除已入队曲目，容量超限不部分写入。首页集合使用原集合加载器，由用户点击触发，30 秒截止、窗口卸载或房间变化取消。FM/心动及不支持卡片显示提示。添加过程和最终结果共用 store 提示，成功不重复弹窗，离开/账号变化回收提示。

播放历史复用原统计会话，在曲目首次实际播放时记录，暂停/恢复不重复；仅恢复但未播放的歌曲不写入。没有新增服务器历史上报或第二套听歌计时。

## 请求数量与播放反馈

- 歌单用一次增量 ADD，不逐首写入；发送前读取最新版本、发送后最多三次读取确认（0/300/900ms），确认完成不再追加 mutation 的重复读取。未知写入不重放，所有等待随服务停机 AbortSignal 回收。
- 确认 HTTP 429 才进入该 transport 的账号冷却：优先 Retry-After 秒数或日期，缺失/非法用 60 秒；冷却期不继续发请求，换账号清空冷却。不会将本机 IPC 忙碌、播放进度异常或普通报错推断成服务器 429。现有 Windows 日志没有证明这次故障源于 HTTP 429。
- 暂停/继续复用前端拖动保护，立即改变本地播放态并维持引擎进度；匹配的服务端回显不强制 seek。原有 3 秒小偏差容差保留，大偏差及新远端操作仍校准。匹配确认立即清理保护定时器，不再多读一次房间；失败或超时只读核验，15 秒操作截止及卸载回收不变。
- PC eapi 域名、加密、Cookie/CSRF、commandInfo/playlistParam 字段、毫秒单位及版本向量规则保持不变。调整的是客户端何时读取、如何确认、何时回收，以及合并明确支持的批量 ADD，不能声称完全复制原版请求时序。

## 独立诊断日志

入口在消息页右上角的“一起听调试”窗口。开关默认关闭，仅本次应用启动有效；普通一起听窗口及正常设置页不增加调试项。

- “打开日志目录”使用 Electron 原生目录打开接口，目录由现有 userData 路径派生，Windows、macOS 和 Linux 共用实现；便携版也跟随原路径。
- 目录为 `{userData}/app-data/logs/together-debug`，当前文件 `current.jsonl`，上一轮转文件 `previous.jsonl`，各自最多约 2MiB。
- 记录匿名房间状态、成员和歌曲数量、指令版本、进度样本、操作耗时、安全错误码，以及 ADD 的布尔 ACK 和读取确认次数。相同状态去重、进度按秒采样，待写队列上限 64 条，超载丢弃后续记录，避免影响播放。
- 不记录账号 UID、昵称、头像、歌曲 ID、房间 ID、Cookie、聊天正文、完整邀请链接、原始请求或响应、任意错误正文。固定字段白名单即使误传整份响应也不落盘其余字段。
- 关闭停止采集并排空队列；整体退出复用原退出等待过程排空日志。没有新增周期任务；磁盘失败自动停止采集，不抛出浏览器进程异常。
- 目前按最新要求先用独立文件；后续迁入原生日志体系时可保留同一匿名事件格式，不把开关或独立日志误称为已经完成迁移。

## 尚不能复原的手机卡片

本轮只读样本确认：手机上的一起听时长总结，在 PC 私信接口中仅返回 `type=6` 和“不支持展示该内容，请前往移动端查看”普通字符串；对应行没有时长、成员或详情链接字段。客户端无法凭此还原历史总结，不能以当前房间时长或截图猜测填充。保留安全文字显示，待取得手机真实结构化载荷后再扩展适配器；移动端抓包仍按用户要求置后。

## 验收范围

自动检查覆盖失败重发、重复点击、账号切换、上拉历史、日期与午夜、锚点及中断贴底、图片迟到解码、ADD 版本刷新与延迟回显、未知写入不重放、取消等待、日志脱敏和轮转。真实双端、滚动视觉、弱网、Mac 实机退出与旧版保数据覆盖升级仍由用户验收。云端构建结果暂不轮询，待本地完成后上传当前源码供构建。
