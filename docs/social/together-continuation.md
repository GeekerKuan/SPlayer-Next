# 房间自动续歌与房主无响应接续

新建房间的进度初始化与调试入口调整先完成，再实现本计划。该能力是 SPlayer 的接续策略，使用已核验的队列 ADD 和播放指令；不宣称复刻未确认的在线上报、服务器角色转移或双人口味算法。

1. 自然播放结束仍由原播放器结算统计和定时关闭。只有未触发定时关闭时，向主进程提交房间、歌曲、指令版本；主进程同时核对真实引擎已结束，拒绝旧歌曲或旧房间事件。
2. 主进程复用已有房间轮询。房主立即接续；房员先等待四秒并重新读取服务端，只有歌曲与指令都未变化时，按房员 UID 选出一个接续者。这个判断是房主未响应，不等于已经证明房主离线，也不改变 creatorId。
3. 普通队列仍有下一首时直接播放下一首。默认开启推荐自动续歌：到达列表末尾后，优先使用未入队的房间推荐，否则使用执行账号的每日推荐。一次最多补一首，读取确认后播放；不替换现有列表。房员没有可用房间推荐时只能取本账号推荐，不能伪称获取离线房主的个人口味。
4. 单曲循环沿用原歌曲，不加歌；服务端 heart 和未知模式不插入个人推荐。关闭自动续歌仅关闭推荐补歌，已有列表和房主无响应接续仍有效。
5. 等待下一首期间保留房间列表，但不重新加载已结束的歌曲。手动操作、新指令、房间变化、断线退出和账号销毁使等待失效；所有等待都附着在已有轮询上，不创建额外常驻定时器。
6. 结果未知的加歌不重复发送：只读确认队列后才能发下一步切歌。结果未知的切歌不重放，显示可手动切歌的提示。多设备并发通过版本重读与房员选举减少重复；现有接口没有已验证的原子跨客户端锁，不能承诺消除同账号多实例的所有竞态。

验证重点为正常队列接续、推荐补歌、房员等待、远端先切歌、重复结束事件、单曲循环、heart 模式、未知写入、取消和资源回收。双端长时实测仍由用户执行。
